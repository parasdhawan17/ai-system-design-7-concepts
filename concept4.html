Concept 4 of 7

Agents — Systems That Plan, Use Tools, and Act

An agent is more than a chatbot. It plans steps, calls tools, checks results, and keeps going until the job is done.

THE BIG IDEA

From answering to doing

A chatbot answers once. An agent works on a goal over many steps.

It breaks the goal into steps. It calls tools. It reads the results. It changes its plan if needed. It stops when the job is done.

Note: the Reel’s card for this concept could not be read clearly, so this chapter teaches the standard study material for Agents in the same simple style.

THE LOOP

Plan, act, observe, repeat

  1. Plan: The model reads the goal and picks the next step.
  2. Act: It calls a tool: search, code, database, API, browser.
  3. Observe: It reads the tool result.
  4. Repeat: It plans again with the new facts, until the goal is met or a limit is hit.
PartRole
ModelThe brain. It reasons and decides.
ToolsThe hands. They do real work in the world.
MemoryShort-term: the current conversation. Long-term: stored facts and past results.
Harness / scaffoldThe system around the model. It runs the loop, passes tool results, and enforces limits.
DESIGN CHOICES

What interviewers probe

  • Single agent vs multi-agent: One agent is simpler. Many agents can split big work, but they add cost and coordination problems. Start with one.
  • Step and cost limits: Set max steps, max time, and max budget. An agent without limits can loop forever.
  • Checkpoints: Save state at safe points. A long job can resume after a failure.
  • Human in the loop: Ask a human to approve risky or irreversible actions.
Key riskErrors compound. 95% success per step over 20 steps is only about 36% success overall. Short plans, verification steps, and retries matter.
DEEP DIVE · PATTERNS

Three common agent designs

PatternHow it worksBest for
ReActReason, act, observe — one step at a time, in a loop.Most tasks. Simple and flexible.
Plan and executeWrite a full plan first. Then execute steps. Re-plan if a step fails.Long tasks where order matters and steps are costly.
ReflectionThe agent reviews its own output, critiques it, and improves it.Writing and code, where a second pass finds real errors.

Multi-agent: a supervisor agent splits work and gives parts to specialist agents. It helps when sub-tasks are truly independent, like research on five companies in parallel. It hurts when agents must agree step by step — messages grow, costs grow, and errors multiply. Default to one agent. Add agents only with a clear reason.

DEEP DIVE · TOOLS

Tool design decides agent quality

  • One tool, one job. A tool named search_orders beats a tool named do_everything.
  • Clear descriptions. The model picks tools from their descriptions. Write them like documentation for a new engineer.
  • Small, typed inputs. Few required fields. Valid values listed. The model makes fewer mistakes.
  • Useful errors. Return what went wrong and what to try next. The agent can only fix errors it can read.
  • Idempotent actions where possible. If the agent retries, the same call should not charge twice or book twice.
  • Least privilege. Read-only by default. Write access only where the task needs it.
WORKED EXAMPLE

A research agent, step by step

Goal: "Compare the pricing of our 3 rivals."

Plan:  1) list rivals  2) visit each pricing page
       3) extract plans  4) build a comparison table

Loop:  search -> read page -> save facts -> next rival
Check: every price must have a source URL
Stop:  table complete, or 25 steps, or $2 budget
Human: approves before the report is emailed

Notice the three safety parts: a verification rule (source URL), hard limits (steps and budget), and a human gate before an external action (email).

RELIABILITY MATH

Why long chains fail

95% per step × 20 steps ≈ 36% success  ·  99% per step × 20 steps ≈ 82% success

Fixes that work: shorter plans, a verify step after risky actions, retries with a different approach (not the same failed call), checkpoints so work is not lost, and a fallback to a human when confidence is low.

Observability: log every step as a trace — plan, tool, input, output, cost, time. Without traces, agent bugs are impossible to debug and evals are impossible to build.

Design checklistGoal is clear · tools are small and well described · step, time, and budget limits set · risky actions need approval · traces logged · retries are idempotent · fallback to human exists.

Interview Q&A

  1. When should an agent ask a human?
  2. Single agent or multi-agent?
  3. How do you debug a failing agent?
When should an agent ask a human?

When the action is irreversible, costly, or low-confidence: sending money, deleting data, emailing customers. The agent prepares everything, the human approves, then it acts.

Single agent or multi-agent?

Start with a single agent and good tools. Most tasks do not need more. Choose multi-agent only when sub-tasks are independent and can run in parallel, and accept the extra cost and coordination.

How do you debug a failing agent?

Read the trace. Find the first step where the plan, tool choice, or tool result went wrong. Most failures are tool design or missing context, not model intelligence.

Quick quiz

  1. Why is an agent harder to control than a single LLM call?
Show answer

It acts over many steps. Each step can add an error, and errors compound. It also changes real state, so mistakes have real effects.
