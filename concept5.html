Concept 5 of 7

Caching — Make It Faster and Cheaper

Do not pay twice for the same work. Cache embeddings, retrieval, answers, and tool results — and know when a cache entry dies.

THE BIG IDEA

The goal: skip repeated expensive work

LLM calls are slow and costly. Many requests repeat, or nearly repeat.

Caching stores a result once. The next similar request reuses it. The system becomes faster and cheaper.

LAYERS

Four places to cache

LayerWhat you store
Embedding cacheThe embedding of a text you have seen before.
Retrieval cacheThe chunks found for a repeated search.
LLM response cacheThe final answer for a repeated question.
API / tool cacheResults from slow or paid external calls.
TWO TYPES

Exact vs semantic

Exact caching: Same request, same response. Simple and safe. It misses small wording changes.

Semantic caching: Different wording, same intent. It embeds the question and reuses an answer for a close match. It hits more often, but a wrong match gives a wrong answer. Set the similarity threshold with care.

THE HARD PART

Invalidation: when does the cache die?

The real question is not “can we cache this?” The real question is “when does it become invalid?”

  • Use a TTL (time to live). Entries expire after a set time.
  • Use version keys. When a document changes, its cache key changes.
  • Never cache answers that must be live, like stock prices or account balances.
  • Never share one user’s cached private data with another user.
Interview line“Freshness beats speed. A fast stale answer is a wrong answer.”
DEEP DIVE · MORE CACHE TYPES

Two caches with special names

Prompt caching (provider cache): Many LLM APIs can cache the repeated start of your prompt — the long system prompt and fixed documents. You pay less and wait less for the repeated part. The changing user question stays uncached at the end. Order matters: put stable text first, changing text last.

KV cache: Inside the model server, attention values for tokens already processed are stored and reused during generation. You do not build this yourself, but it explains why long shared prefixes are cheap and why serving systems group similar requests.

DEEP DIVE · KEYS AND TTL

How cache entries are named and killed

DecisionSimple rule
Cache keyHash of the full request: model, prompt version, user rights, language, and inputs. Change any part, get a new key.
TTLMatch the data. News: minutes. Product docs: hours to days. Static FAQs: days, with manual clear on publish.
Version in keyPut the document or prompt version in the key. New version means old entries are never read again. This is the safest invalidation.
Stampede guardWhen a hot entry expires, many requests rebuild it at once. Use a lock so one request rebuilds and the rest wait or serve the old entry briefly.
WORKED EXAMPLE

What caching saves, in numbers

10,000 questions per day
 60% are repeats or near-repeats (FAQ traffic)
 LLM call cost: $0.01, latency: 2 seconds
 Cache hit cost: near $0, latency: 50 ms

Without cache: $100/day, every user waits 2 s
With cache:    $40/day, 60% of users wait 50 ms

Measure the hit rate per cache layer. A layer with a 2% hit rate and high complexity should be removed.

MISTAKES AND FIXES

Cache with care

MistakeFix
Caching personalised answers in a shared cacheInclude the user or rights group in the key. Never leak across users.
Semantic threshold too looseWrong answers get reused. Raise the threshold, and test the cache like an eval.
No TTL “because data rarely changes”Rarely is not never. Always set a TTL or a version key.
Caching errors and empty resultsCache successes only, or use a very short TTL for failures.
Design checklistStable prompt prefix first · key contains versions and user scope · TTL matches data freshness · hit rate measured per layer · semantic threshold tested · private data never shared.

Interview Q&A

  1. Exact cache or semantic cache for support FAQs?
  2. What should never be cached?
  3. How do you invalidate after a document update?
Exact cache or semantic cache for support FAQs?

Use both. Exact cache catches copy-paste repeats at zero risk. Semantic cache catches rephrased questions, which is most FAQ traffic — but test its threshold like an eval, because a wrong match serves a wrong answer fast.

What should never be cached?

Live or personal data: balances, prices that move, stock levels, and anything private to one user in a shared store. Also never cache a guardrail decision for a different user.

How do you invalidate after a document update?

Version keys. The updated document gets a new version, so retrieval and answers built on the old version are never served again. Add a TTL as a backstop.

Quick quiz

  1. A user asks the same question in different words. Which cache helps?
Show answer

Semantic caching. It compares meaning, not exact text. Exact caching only hits when the request is identical.
