Concept 6 of 7

User Feedback Loops — Learn From Real Users

Real users find failures your tests missed. Collect their signals, find the root cause, fix it, and turn the fix into an eval.

THE BIG IDEA

The goal: improve from real use, forever

Offline evals use test data. Real users use the system in new ways.

They find new failures every day. A feedback loop turns those failures into fixes. The system gets better over time.

SIGNALS

What counts as feedback

  • Explicit: Thumbs up or down, ratings, written corrections.
  • Retries: The user asks again, or rephrases. The first answer probably failed.
  • Escalations: The user asks for a human. The agent reached its limit.
  • Abandoned workflows: The user starts a task and leaves. Something blocked them.
CAUTION

Feedback is not ground truth

A thumbs down does not tell you what broke. It can mean five different things:

  • The answer was wrong.
  • Retrieval fetched the wrong documents.
  • The needed information was missing.
  • The product experience was bad.
  • The user misunderstood the answer.

So do not train blindly on raw feedback. First find the real cause.

THE LOOP

Six steps, repeated

  1. Collect user feedback.
  2. Investigate the case. Read the transcript.
  3. Find the root cause.
  4. Fix the cause: data, retrieval, prompt, or model.
  5. Create a new eval from this case.
  6. Run the eval suite. Prevent the same regression.
Key point from the ReelConvert important feedback into permanent engineering knowledge. That knowledge is an eval. Now the failure can never return silently.
DEEP DIVE · READING SIGNALS

Strong signals vs weak signals

SignalStrengthWhat it often means
User corrects a factStrongA real error with the correct answer attached. Gold for evals.
User escalates to a humanStrongThe agent failed the task or the user lost trust.
User rephrases and retriesMediumThe first answer missed the intent or the facts.
Thumbs down, no commentWeak aloneSomething was wrong. You must investigate to learn what.
Long pause, then abandonWeak aloneConfusion, slowness, or life interrupting. Check the transcript.

Weight strong signals first in your review queue. They carry the diagnosis with them.

DEEP DIVE · TRIAGE

From 1,000 feedback items to 5 fixes

  1. Group: Cluster similar complaints. “Wrong refund amount” may appear 80 times in different words.
  2. Count and weigh: Score each cluster by frequency × user impact. A rare payment error can beat a common typo.
  3. Diagnose: For the top clusters, read full transcripts. Name the root cause: data, retrieval, prompt, model, tool, or UX.
  4. Fix the cause, not the single example. A prompt tweak that fixes one phrasing may break ten others — the eval suite will tell you.
  5. Convert: Each fixed cluster becomes new eval tasks before the fix ships.
WORKED EXAMPLE

One thumbs down becomes armour

Feedback:  thumbs down on a refund answer
Read:      transcript shows policy chunk from last year
Cause:     index still holds the old policy version
Fix:       version keys in the index + old version deleted
Eval:      12 new tasks on refund limits, old and new
Result:    regression suite now guards refund answers forever
PITFALLS

Four ways teams misuse feedback

  • Loud minority: Power users give most feedback. Check if a complaint is common or just loud, using counts.
  • Training on raw feedback: Users can be wrong, rude, or gaming the system. Verify before you teach.
  • Only happy-path metrics: Average rating can rise while one segment fails completely. Slice feedback by task, language, and user type.
  • No closing of the loop: Tell users when their report fixed something. Teams that close the loop get more and better reports.

Drift: User needs and data change over time. A weekly feedback review catches drift that quarterly planning misses.

Design checklistSignals collected in product · strong signals reviewed first · clusters scored by impact · root cause named before any fix · every fix ships with new evals · results reported back to users.

Interview Q&A

  1. How is a feedback loop different from evals?
  2. Users disagree with each other in feedback. Who wins?
  3. What is the first metric you watch in a feedback loop?
How is a feedback loop different from evals?

Evals test with prepared tasks before release. Feedback loops learn from real users after release. The bridge: feedback cases become new eval tasks, so each real failure is tested forever.

Users disagree with each other in feedback. Who wins?

Neither, automatically. Segment the feedback: different users may need different behaviour, or one group may be misusing the feature. Decide from product goals and measured impact, not volume of complaints.

What is the first metric you watch in a feedback loop?

Escalation and retry rates by task. They are strong, honest signals. Star ratings are easy to collect but hard to interpret.
