Concept 3 of 7

Evals — Know If the System Works

Evaluations are tests for AI systems. They show if a change helped or hurt, before users find out.

THE BIG IDEA

The goal: measure, do not guess

Without evals, teams fix one failure and create another. They learn about problems only from user complaints.

With evals, every failure becomes a test case. Every change is measured against the same tests. This chapter follows Anthropic’s “Demystifying evals for AI agents”, the article shown in the Reel.

THE WORDS

Seven words you must know

WordSimple meaning
TaskOne test, with clear input and clear success rules.
TrialOne try at a task. Run many trials, because answers change.
GraderLogic that scores the result. One task can have many graders.
TranscriptFull record of one trial: messages, tool calls, and steps.
OutcomeFinal real state. A booking in the database — not “Done!” in chat.
Eval harnessThe system that runs tasks, records steps, and grades results.
Eval suiteA group of tasks for one goal, like refunds and cancellations.
GRADERS

Three types of graders

GraderBest for
Code-basedExact checks: match, regex, schema, unit tests, simple rules. Fast and deterministic.
Model-basedLLM as judge: rubric scoring and pairwise comparison for open answers, tone, and quality.
HumanExpert judgement for difficult cases and golden tasks. Slow, so use it to calibrate the others.

Capability evals ask “what can it do?” Use hard tasks. The score starts low. Regression evals ask “did something break?” The pass rate must stay high, near 100%.

MANY TRIALS

pass@k vs pass^k

pass@k: at least 1 success in k tries. The score rises with k. pass^k: all k tries succeed. The score falls with k.

75% per trial  →  pass^3 = 0.75³ ≈ 42%
Start smallStart with 20–50 tasks from real failures. Write a reference solution for each task. If a strong model scores 0% on many trials, the task is probably broken — check the task and grader first. Opus 4.5 went from 42% to 95% on CORE-Bench after grader bugs were fixed.
DEEP DIVE · THE ROADMAP

From zero to trusted evals in 8 steps

  1. Start early. 20 to 50 tasks from real failures is a strong start.
  2. Reuse manual checks. Turn release checks, bug reports, and support tickets into tasks.
  3. Write clear tasks. Two experts must reach the same verdict. Add a reference solution for each task.
  4. Balance the set. Test should-do and should-not-do cases in similar numbers.
  5. Build a clean harness. Each trial starts from a fresh, isolated environment.
  6. Design graders with care. Code where possible, model where needed, humans to calibrate. Grade outcomes, allow partial credit.
  7. Read transcripts. Scores without reading hide broken tasks and unfair graders.
  8. Watch saturation and maintain. Add harder tasks as scores climb. Give the suite a clear owner.
DEEP DIVE · EVAL TYPES

Three shapes of agent evals

TypeWhat it checksExample
Single-turnOne input, one output.Classify this ticket correctly.
TrajectoryThe sequence of tool calls and steps.Did the agent search before it answered?
End-stateThe final state of the environment.Is the refund present in the database?

For conversational agents, add a second LLM that plays the user. Then grade the end state, the turn count, and the tone together.

Benchmarks you may hear: SWE-bench Verified (coding fixes), Terminal-Bench (end-to-end technical tasks), τ²-Bench (multi-turn support and booking), BrowseComp (hard web research), WebArena and OSWorld (computer use).

DEEP DIVE · LLM AS JUDGE

Make model grading trustworthy

  • Write a rubric: clear levels with examples, not “be good”.
  • Use one judge per dimension: facts, tone, completeness — separate judges.
  • Give the judge a way out: it may answer “Unknown” instead of guessing.
  • Calibrate with humans: humans grade a sample; measure how often the judge agrees. Recheck on a schedule.
  • Prefer pairwise judging for style: “which answer is better?” is easier than an absolute score.
NUMBERS AND GATES

Evals in the release pipeline

Run evals in CI, like unit tests. A change cannot ship if the regression suite drops. Track four numbers for every run: pass rate, cost per task, latency, error rate.

Example gate: regression suite must stay at 98% or above; capability suite is reported, not gated. When a capability task reaches near 100% for weeks, graduate it into the regression suite.

Design checklistTasks from real failures · reference solution per task · balanced should / should-not · isolated trials · outcome graded first · judges calibrated · regression gate in CI · transcripts read weekly.

Interview Q&A

  1. Your eval score suddenly drops 30 points after a model upgrade. First move?
  2. Capability eval or regression eval — which one gates a release?
  3. How do you stop agents cheating an eval?
Your eval score suddenly drops 30 points after a model upgrade. First move?

Read transcripts before blaming the model. Check three suspects in order: broken tasks, grader bugs, and harness limits. Only then judge the model. Anthropic found exactly this pattern on CORE-Bench: 42% was a grading problem, the fixed score was 95%.

Capability eval or regression eval — which one gates a release?

The regression suite. It must stay near 100%, so a drop means something broke. Capability evals guide development; they start low by design and are reported, not gated.

How do you stop agents cheating an eval?

Grade real end-state, hide test details from the agent, vary tasks, and read transcripts. If passing is easier by a loophole than by solving, agents will find the loophole.

Quick quiz

  1. Per-trial success is 75%. What is pass^3, and why does it matter?
Show answer

0.75 × 0.75 × 0.75 ≈ 42%. It matters for user-facing agents: users need success every time, not once in three tries.
