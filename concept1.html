Concept 1 of 7

RAG — Give the Model the Right Knowledge

Retrieval-Augmented Generation. The model does not know your data. You fetch the right data and give it to the model at answer time.

THE BIG IDEA

The goal: right knowledge, at answer time

An LLM knows only its training data. It does not know your company files. It does not know data from today.

RAG fixes this. First you search your documents. Then you give the best pieces to the model. The model answers using those pieces.

Simple ruleGood retrieval = good context = good answer. Bad retrieval = bad answer, even with a great model.
HOW IT WORKS

The RAG pipeline, step by step

  1. Load: Collect documents: PDFs, web pages, tickets, manuals.
  2. Chunk: Split documents into small pieces. Each piece is a chunk.
  3. Embed: Turn each chunk into numbers (an embedding). Similar meanings get similar numbers.
  4. Store: Save chunks and embeddings in a vector database.
  5. Retrieve: Embed the user question. Find the chunks with the closest meaning. This is top-k retrieval.
  6. Rerank: Score the found chunks again, with a stricter model. Keep only the best.
  7. Generate: Send the question plus the best chunks to the LLM. Ask it to answer from the chunks and cite them.
KEY DETAILS

What decides RAG quality

ChoiceWhy it matters
Chunk sizeToo small: the chunk loses meaning. Too big: the chunk adds noise and cost.
OverlapChunks share some text at the edges. Ideas are not cut in half.
MetadataTags like date, product, and source let you filter the search.
Embedding modelIt decides what “similar” means. A weak model finds weak matches.
Hybrid searchMix keyword search (exact words) with vector search (meaning). Each covers the other’s misses.
FreshnessUpdate the index when documents change. Old chunks give old answers.
COMMON FAILURES

Four ways RAG breaks

  • Wrong or irrelevant documents are retrieved.
  • Poor chunking cuts the key fact away from its context.
  • Too much context confuses the LLM. More is not always better.
  • The model hallucinates even with the correct context in front of it.
Interview line“When a RAG answer is wrong, I debug retrieval first, not the prompt. Most RAG bugs are retrieval bugs.”
DEEP DIVE · CHUNKING

How to cut documents well

Chunking is the most important RAG choice. A bad cut can hide the answer.

MethodHow it cutsUse it when
Fixed sizeEvery N tokens, with overlap.Simple start. Plain, uniform text.
RecursiveCut by paragraphs first. Then by sentences. Then by words.Most documents. It respects natural breaks.
Structure-basedCut by headings, sections, or code functions.Manuals, docs sites, and code. Each chunk is one topic.
SemanticCut where the topic changes, using embeddings.Long articles with many topics. It costs more to build.

Useful starting numbers: chunk size 256 to 1,000 tokens. Overlap 10% to 20% of the chunk size. Then measure and adjust. There is no magic number. Your documents decide.

Keep the source title and heading inside each chunk, or as metadata. A chunk that says “the limit is 30 days” is useless if no one knows which policy it came from.

DEEP DIVE · BETTER RETRIEVAL

Four tricks that raise answer quality

  • Query rewriting: The user asks in short, messy words. Rewrite the question into a clear search query before you search. Add missing context from the chat history.
  • Multi-query: Make 3 to 4 versions of the question. Search with all of them. Merge the results. This finds documents that one wording misses.
  • HyDE: Ask the LLM to write a fake draft answer. Embed the draft and search with it. A draft answer is often closer in wording to the real document than the question is.
  • Metadata filtering: Filter first by product, date, language, or user rights. Then search inside the smaller set. This stops wrong-product answers.

Reranking detail: Vector search is fast but rough. It returns the top 20 to 50 chunks. A reranker is a slower, smarter model. It reads the question and each chunk together and sorts them well. You keep the top 3 to 8 chunks for the final prompt.

WORKED EXAMPLE

One question, end to end

User: "Can I return shoes after 40 days?"

1. Rewrite  -> "shoes return policy time limit days"
2. Filter   -> product = shoes, region = user region
3. Search   -> hybrid: keyword + vector, top 30 chunks
4. Rerank   -> keep top 5 chunks
5. Prompt   -> question + 5 chunks + "answer only from sources, cite them"
6. Answer   -> "No. The limit is 30 days for shoes. [Policy v3, Returns]"
7. Outcome  -> answer is grounded, cited, and fresh

If step 3 finds chunks about clothes, the answer will be wrong even if steps 5 to 7 are perfect. This is why you debug retrieval first.

MEASURE IT

How to know your RAG works

CheckQuestion it answers
Retrieval recallDid search find the chunk with the true answer?
FaithfulnessDoes the answer use only facts from the chunks?
Answer relevanceDoes the answer address what the user asked?
Citation accuracyDo the cited sources really support the claims?

Test retrieval alone, before you test full answers. If recall is low, no prompt can save the system.

Design checklistChunks respect document structure · metadata on every chunk · hybrid search on · reranker on · index updates when documents change · answers cite sources · per-user access filter before search.

Interview Q&A

  1. How do you reduce hallucination in a RAG system?
  2. Vector search or keyword search — which one?
  3. How often should the index update?
How do you reduce hallucination in a RAG system?

Improve retrieval first: better chunks, hybrid search, reranking. Then force grounding: tell the model to answer only from the given chunks and to say “I do not know” when the chunks have no answer. Add citations so users can verify.

Vector search or keyword search — which one?

Both. Keyword search (BM25) is best for exact words like product codes and names. Vector search is best for meaning. Hybrid search merges both result lists, then a reranker sorts the final set.

How often should the index update?

As often as the source changes. Prices and stock: near real time or do not index them at all. Policies and manuals: on every publish. Use document version IDs so old chunks are deleted, not just replaced.

Quick quiz

  1. Why can a RAG system give a wrong answer even when the correct document exists in the database?
Show answer

Bad retrieval or bad chunking can fetch the wrong pieces. Too much context can also confuse the model. And the model can still hallucinate. Retrieval quality is the limit.
